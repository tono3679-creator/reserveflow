# アーキテクチャ

ReserveFlow は、美容室・整体院・パーソナルジム・レンタルスペースなど複数業種で使える予約・顧客管理 SaaS です。
1つのアプリ・1つのデータベースで複数の企業（テナント）を扱い、業種の違いは「設定とデータ」で表現します。

## 1. 要件の整理

| 区分 | 内容 |
| --- | --- |
| 利用者 | 店舗のオーナー／マネージャー／スタッフ、予約するお客様、ポートフォリオの閲覧者（デモ） |
| 中心機能 | 予約カレンダー・予約 CRUD（競合防止つき）、顧客・スタッフ・サービス管理、公開予約ページ |
| 差別化 | スマート空き枠提案（ルールベース）、無断キャンセル分析、リピート率分析（コホート） |
| 非機能 | テナント分離（RLS）、権限（画面・サーバー・DB の3段）、UTC 保存＋店舗タイムゾーン表示、PC/スマホ対応 |
| 外部依存 | AI API なし。メールはアダプター（キー未設定ならデモ通知として画面で確認） |

### 仕様にない点で決めた初期値

- **企業と店舗**：`organizations`（企業）と `locations`（店舗）を分ける。予約・スタッフ・サービス・営業時間は店舗単位、顧客は企業単位（同じ企業の複数店舗で顧客を共有できる）。
- **権限は企業単位**：`organization_members.role` が owner / manager / staff。staff はログインと `staff`（担当者）を結び付けて「自分の予約」を判定する。
- **マネージャーと売上**：仕様どおり「売上閲覧」はオーナーのみ。マネージャーは予約・顧客分析（無断キャンセル・リピート）とスタッフ別の件数は見られるが、売上分析画面と売上の KPI は見られない。
- **枠を占有する予約ステータス**：予約確定・来店済み・サービス完了。顧客キャンセル・店舗キャンセル・無断キャンセルになった予約は枠を解放する（無断キャンセルは終了後に確定することが多く、同じ時間の飛び込み対応を妨げないため）。
- **必要設備**：サービスに紐づく設備は「このうちどれか1つが空いていれば良い」（例：施術ベッド3台のうち1台）。空いている設備は自動で割り当てる。
- **タイムゾーン**：既定は Asia/Tokyo。予約は `timestamptz`（UTC）で保存し、店舗のタイムゾーンで表示・計算する。
- **予約受付設定の既定**：当日の受付は開始の60分前まで、60日先まで、枠の刻み30分、キャンセル・変更は24時間前まで。
- **金額**：円の整数（最小通貨単位）。他通貨は `tenant_settings.currency` で将来対応。

## 2. 全体構成

```
ブラウザ ── Next.js（App Router, Vercel）
              ├─ Server Components … 画面のデータ取得（サーバーで DB を読む）
              ├─ Server Actions   … 管理画面の更新（フォーム・ダイアログ）
              ├─ Route Handlers   … 公開予約 API（空き枠・予約確定）、Cron（リマインド・デモ片付け）
              └─ src/lib/scheduling … 空き枠探索・スコアリング（画面にも DB にも依存しない純粋な TypeScript）
                     │
                     ▼ postgres.js（サーバーだけが接続。ブラウザは DB に直接触らない）
              PostgreSQL（Supabase）
              ├─ RLS … トランザクションごとに role=authenticated と JWT の sub を設定して効かせる
              ├─ 排他制約 … 同じスタッフ・設備の時間の重なりを DB が拒否する
              └─ 予約の書き込み関数 … 権限・テナント・状態遷移・履歴をまとめて1トランザクションで
```

### データ取得・更新の使い分け

| 用途 | 方式 | 理由 |
| --- | --- | --- |
| 管理画面の表示 | Server Components | DB の結果をそのまま描画。秘密情報をブラウザへ出さない |
| 管理画面の作成・変更 | Server Actions | フォームと相性が良く、Next.js が CSRF 対策（Origin 確認）を行う |
| 公開予約（空き枠・確定・変更） | Route Handlers | ログインなしの公開 API。レート制限と入力検証を1か所で行う |
| 定期処理 | Route Handlers（Vercel Cron） | `CRON_SECRET` で保護 |

### RLS の効かせ方

アプリはサーバーで PostgreSQL に直接接続し、ログイン中の利用者の処理は必ず `asUser()` を通します。
`asUser()` はトランザクションの中で `set_config('role','authenticated')` と `request.jwt.claims`（sub = 利用者 ID）を設定するため、
Supabase の RLS ポリシー（`auth.uid()`）がそのまま効きます。サーバー側でも `requireRole()` で権限を確かめるので、
権限は「画面の表示」「サーバーの処理」「DB の RLS・関数」の3段で判定されます。

### 認証

`AUTH_PROVIDER` で切り替えます。

- `supabase`：Supabase Auth（メール＋パスワード）。`@supabase/ssr` で Cookie を扱い、利用者 ID（sub）を RLS に渡す。
- `local`：アプリ内のログイン（`auth.users.encrypted_password` を bcrypt で照合し、DB のセッション表で管理）。
  Supabase に接続できない開発・テスト環境用。パスワードの形式は Supabase Auth と同じなので、同じ利用者データがどちらでも使える。

デモ利用者はどちらのモードでもアプリのセッション（`app_private.sessions`）で扱います（登録不要・24時間で削除）。

### デモの分離

「デモを体験」を押すと、その訪問者専用の企業4社（美容室・整体院・パーソナルジム・レンタルスペース）を、今日を基準に生成します。
訪問者は自分の企業の中だけで予約の作成・変更・キャンセルができ、共有データは書き換わりません。
オーナー・マネージャー・スタッフの3つの立場を切り替えて、権限の違いも体験できます。24時間後に自動で削除します。

### 空き枠エンジン（src/lib/scheduling）

入力（営業時間・休業日・スタッフ勤務・休暇・既存予約・設備・サービス・受付設定・重み）を受け取り、候補とスコア・理由を返す純粋関数です。
管理画面のスマート空き枠提案、カレンダーの空き表示、公開予約ページの空き時間が同じモジュールを使います。
表示した空きは保証せず、確定時はサーバーで同じ判定をやり直し、最後は DB の排他制約が同時予約を防ぎます。
将来 AI の自然言語提案を加える場合も、このモジュールの入出力をそのまま使えます。

### 通知

予約の確定・変更・キャンセルは DB 関数の中で `notification_events` を作ります（`dedupe_key` が一意なので重複しない）。
リマインドは Cron が前日・当日分を作ります。送信はアダプター（`src/lib/notifications/adapters`）で、
メールのキーが無いときは送らずに「デモ通知」として記録し、通知管理画面で内容を確認できます。

## 3. ディレクトリ

```
src/
  app/
    (marketing)/          トップページ（デモ入口）
    (auth)/login/          ログイン
    (app)/                 管理画面（左サイドバー）
    book/[slug]/           公開予約ページ
    api/                   公開 API・Cron
  components/ui/           shadcn/ui 形式の部品
  components/...           画面ごとの部品
  lib/
    auth/                  認証（supabase / local）と権限
    db/                    接続と asUser()
    scheduling/            空き枠エンジン（純粋関数）
    analytics/             KPI・無断キャンセル率・リピート率（純粋関数）
    notifications/         通知アダプター
    demo/                  デモデータ生成
    validation/            Zod スキーマ
supabase/migrations/       DB スキーマ・RLS・関数（Supabase CLI と同じ形式）
db/local/                  ローカル PostgreSQL で Supabase の土台（auth スキーマ・ロール）を再現する SQL
tests/unit, tests/db, tests/e2e
```

## 4. 開発計画

| Phase | 内容 | 完了の確認 |
| --- | --- | --- |
| 1 基盤 | Next.js・デザインシステム・共通レイアウト・認証・マルチテナント・DB スキーマ・RLS | ビルド、RLS のテナント分離テスト、ログイン E2E |
| 2 予約管理 | スタッフ・サービス・顧客・カレンダー（FullCalendar）・予約 CRUD・競合防止 | 予約の作成・変更・競合のテスト |
| 3 公開予約 | `/book/[slug]`・空き枠 API・確定・変更/キャンセル（トークン）・通知イベント | 公開予約の E2E |
| 4 分析 | ダッシュボード・売上・無断キャンセル・リピート率・スタッフ別 | 計算ロジックのユニットテスト |
| 5 空き枠提案 | 探索・スコアリング・ランキング・理由・カレンダー連携 | エンジンのユニットテスト |
| 6 仕上げ | デモ環境・レスポンシブ・テスト・README・Vercel 公開準備 | 全テスト・ビルド |
